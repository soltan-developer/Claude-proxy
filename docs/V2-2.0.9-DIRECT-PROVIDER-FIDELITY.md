# Claude Proxy 2.0.9 — Direct provider and isolated fidelity diagnostics

## Root causes and confirmed behavior

Windows PowerShell showed HTTPS_PROXY=http://127.0.0.1:10808, an inactive
v2rayN proxy. The provider URL https://ai.ismc.ir/api/v1/models responded
directly with HTTP 401 to a request without API credentials. Earlier
2.0.8 code first tried the inherited proxy before direct recovery, adding
connection-failure delay to *every* provider call. The user explicitly
requires that provider API calls DO NOT use the v2rayN web-search proxy.

Starting with 2.0.9:
- Provider PING, model discovery, chat/completions requests, and continuation
  calls choose a separate reqwest client with no_proxy() by default.
- System/auto is only supported as an EXPLICIT advanced process override
  with CLAUDE_PROXY_PROVIDER_PROXY_MODE=system|auto. Empty/invalid values
  select direct. This override is not controlled by the Web Search UI.
- When the advanced system/auto override is explicitly chosen, the
  separate direct TCP latency probe is skipped and the model fidelity
  probe honors that network policy; it never bypasses a VPN-only setting.
- The Web Search client independently uses no_proxy() for direct mode, or
  ONLY the user-configured manual web proxy (including a supported SOCKS
  URL) in manual mode. Its proxy setting is not reused by the model API.
- The configured local gateway port (such as 18183) is unchanged.
- No secret, prompt, file content, or credential is written to diagnostics.

## What latency actually means

The old button labelled "Ping provider API" was an authenticated HTTPS
GET to /v1/models: the reported time includes DNS, TLS and provider
processing. A 2000 ms model-list response is NOT evidence of 2000 ms
network RTT or ICMP ping.

2.0.9 runs two measurements concurrently and labels them separately:
- direct network TCP connect (including DNS lookup; not ICMP)
- authenticated /v1/models API HTTP response time

Model generation latency (time to first token, tokens/sec) is ANOTHER
metric not implied by either measurement. An Iranian server need not
answer a model API in 50 ms.

## Investigation of unrelated Code/Cowork answers

Windows field test:
- Real Bash pwd succeeded, and returned /d/Work/Software/Claude-proxy.
- Model ignored requested cat README.md and searched unrelated Chinese
  "New Project" text instead.
- For FA-527 and ZH-884 simple instructions it returned unrelated
  GitHub/project-search prompts. These are real functional failures.
- It is not proven whether an upstream server mixes concurrent sessions,
  client chat history was attached, or the upstream model ignored the
  most recent instruction.
- Existing PR #18 reduced unwanted web tool injection and preserved
  client-owned Read/Bash tools; it cannot force third-party models to
  interpret instructions correctly.

New, EXPLICIT "Test upstream model instructions (2 requests)" button
sends two FIXED, synthetic Persian and Chinese prompts to the configured
default upstream model directly via HTTP, with one user turn each and
NO system prompt, chat history, tools, browser, shell, file access,
web proxy or client session. The button reports the model ID, marker
pass/fail, tool-call count, and first 240 returned characters. Each
click invokes TWO real model completions, potentially incurring fees.

Interpretation:
- If this isolated direct probe fails, investigate the provider's
  model routing, response quality, concurrency/session reuse and
  Chat Completions implementation first.
- If both isolated probes pass but Claude Code/Cowork fails, compare
  gateway request metadata (preflight context/message/tool counts),
  actual client conversation and tool results. The proxy/client
  adapter or tool semantics may be the cause.
- If an isolated probe passes, it proves only that tiny test succeeds;
  it DOES NOT guarantee long-context Code/Cowork behavior.
- Never treat model text alone as proof of executing a tool. Confirm
  exact tool_call/tool_result observations.
- The probe result separately shows the requested model, the model ID
  *reported by the upstream response* (or unreported), and response ID (or
  unreported). Do not treat the requested model as proof of actual routing.
- PASS is a conservative smoke check: the marker must be at the end,
  at least two characters of the expected Persian/Chinese writing script
  must be present, and no tool calls may be returned. This does not prove
  complete language comprehension or tool fidelity.
- When an Anthropic user content array mixes tool_result and fresh text,
  Chat Completions must receive the tool message immediately after the
  corresponding assistant tool_call, then a separate user message containing
  the additional instruction. Otherwise the upstream may reject the tool
  transcript or lose grounding. A dedicated regression covers this ordering.

## Connection architecture recovery after real Windows failure

A Windows field attempt showed `error sending request for url (.../v1/models)` even
with the Direct default. This string is a transport error, **not** an HTTP
status. It does not prove the provider is down, nor does it prove that TLS
is the problem.

- The provider network route is now persisted per configuration as `direct`
  (default) or `system` (explicit only). The configured Web Search manual
  proxy is **never** used by provider API calls.
- The model-list connection test uses the SAME route as inference and
  continuation. System routing is optional; it may fail if the user's
  Windows system proxy points to a closed listener.
- On connection failure, a limited, bounded diagnostic separates DNS
  resolution, direct TCP connectivity, and failures after TCP (HTTPS,
  timeout, TLS or HTTP transport). No single stage is named as the root
  cause without direct evidence.
- When the explicitly selected System route fails, direct DNS/TCP probing
  is skipped to avoid an unrelated network disclosure or misleading
  comparison.
- Model discovery saves the model list only after a successful response.
  All existing model routes, API secrets, and local gateway ports stay
  unchanged on a failed connection check.
- The Provider Connection page has one connection/model-discovery action and
  one Save action. Advanced routing is collapsed; manual language-fidelity
  diagnostics and context settings are not inline on the provider page.

## 2.0.9 Greeting/tool-routing regression audit (Draft PR #24)

Observed actual Windows behavior: a Persian "سلام" generated an English
claim that GitHub web search failed. This is not evidence a search was run.

Confirmed code defects:
- Client-owned tools were protected from local tool injection only if
  experimental V2 Enforce was active. Protection is now unconditional.
- Web intent interpreted embedded `<system-reminder>` and
  `<environment_context>` control content as user intent. This context
  is now excluded **only for the intent router**; the original request is
  not modified.
- Incidental repository names and historical context no longer force a
  new local web tool call; explicit user searches retain web access.

Every request now logs a sanitized "tool routing" audit event with client
tool count, local web/shell injection status, tool_choice status and ID
even when V2 contracts are Off. Non-streaming responses log provider
tool-call count under "provider response shape". No prompt, response text,
API key, tool arguments or local file paths are logged.

Acceptance: run a new empty chat on Windows, send "سلام", and check the
"tool routing" record in Diagnostics. `local_web=false` means the proxy
did not add local web search tools for that request. If the upstream
still talks about GitHub search, inspect the client system/history and
upstream model behavior; do not claim local web was executed.

Tests use local HTTP mocks and prove only the gateway's routing behavior,
not actual Qwen response quality. Keep PR Draft until user accepts.

## Cowork native tools / fresh-greeting forensic finding (PR #25)

Evidence: local report dated 2026-10-10, 07:22:10 UTC, for a newly
opened Cowork chat where the only visible message was Persian "سلام":
- `client_tools=38`, `client_messages=2`, `client_tools_owned=true`.
- `web_intent=NoWeb`, `local_web=false`, `local_shell=false`.
- `inbound_greeting=true`, `outbound_greeting=false` using an
  earlier **heuristic** of stripped/flattened user text. That mismatch
  does **not** prove the source text changed or that sessions leaked.
- `Proactive context budgeting removed 1 older conversation turn`,
  despite being the start of a visible Cowork conversation. The agent
  can still send hidden bootstrap turns.
- The visible Cowork client executed its own `Bash` and `List sessions`
  tools. This proves neither an upstream-model tool-request bug nor a
  local Proxy Shell/Web execution. An unnecessary tool call can be a
  provider/model agent-routing failure.

Confirmed defect: the gateway uses an approximate token estimate and
has auto-trim ON by default, so native-agent bootstrap messages could be
discarded without user approval, even when the client owns 38 tools.
Fix: **never auto-trim a request with client-owned tools** (neither on
the first budget pass nor in an HTTP context-overflow retry). Preserve
the original request and surface `COWORK_CONTEXT_TOO_LARGE` instead
of suppressing the failure or pretending the model saw all context.

Diagnostic improvement: `last_user_text_preserved` is a privacy-safe
boolean comparing the pre-conversion and post-conversion *text*.
Unlike `inbound_greeting` and `outbound_greeting`, this measures
equality directly without logging/hashing any text. It is a wire
text-only check, not a complete comparison of files/images/tools.

A local end-to-end HTTP test exercises a short Cowork request with a
bootstrap user message, a greeting, client-owned Bash tool schema,
web bridge configured as required and an intentionally small configured
context window. Both user turns and native tools must reach the mock
provider intact.

**Follow-up acceptance on Windows:**
1. Launch the artifact from the exact green head SHA; fully exit any old
   Windows process from the tray before starting it.
2. In a *new* Cowork chat send only `سلام`.
3. Inspect `request provenance`: text-preserved flag, inbound/outbound
   greeting classification, message counts and agent ownership.
4. Confirm **no context auto-trim** warning for that Cowork request.
5. Note native tools may still be called by a poorly matched upstream

6. Real UI-based Cowork acceptance is pending; do not claim full fix.

Existing stored credentials and model settings unchanged. No new UI
buttons, external provider requests, public release or merge.

### Additional confirmed context truncation bug

The old `trim_oldest_turn` function treated the span between any two
`user` messages as a completed historical turn, **even if it contained
zero `assistant` responses**. A Cowork bootstrap user message followed
by the visible "سلام" thus qualified for silent deletion before any
model action. A complete removable turn now requires an intervening
assistant reply. A focused regression proves that back-to-back user
instructions are kept intact, even when automatic trimming is enabled
and the budget is critically small.
