# Claude Proxy 2.0.9 — Direct provider and isolated fidelity diagnostics

## Root causes and confirmed behavior

Windows PowerShell showed HTTPS_PROXY=http://127.0.0.1:10808, an inactive
v2rayN proxy. The provider URL https://ai.ismc.ir/api/v1/models responded
directly with HTTP 401 to a request without API credentials. Earlier
2.0.8 code first tried the inherited proxy before direct recovery, adding
connection-failure delay to *every* provider call. The user explicitly
requires that provider API calls DO NOT use the v2rayN web-search proxy.

Starting with 2.0.9:
- Provider PING, model discovery, chat/completions requests, and continuation
  calls choose a separate reqwest client with no_proxy() by default.
- System/auto is only supported as an EXPLICIT advanced process override
  with CLAUDE_PROXY_PROVIDER_PROXY_MODE=system|auto. Empty/invalid values
  select direct. This override is not controlled by the Web Search UI.
- When the advanced system/auto override is explicitly chosen, the
  separate direct TCP latency probe is skipped and the model fidelity
  probe honors that network policy; it never bypasses a VPN-only setting.
- The Web Search client independently uses no_proxy() for direct mode, or
  ONLY the user-configured manual web proxy (including a supported SOCKS
  URL) in manual mode. Its proxy setting is not reused by the model API.
- The configured local gateway port (such as 18183) is unchanged.
- No secret, prompt, file content, or credential is written to diagnostics.

## What latency actually means

The old button labelled "Ping provider API" was an authenticated HTTPS
GET to /v1/models: the reported time includes DNS, TLS and provider
processing. A 2000 ms model-list response is NOT evidence of 2000 ms
network RTT or ICMP ping.

2.0.9 runs two measurements concurrently and labels them separately:
- direct network TCP connect (including DNS lookup; not ICMP)
- authenticated /v1/models API HTTP response time

Model generation latency (time to first token, tokens/sec) is ANOTHER
metric not implied by either measurement. An Iranian server need not
answer a model API in 50 ms.

## Investigation of unrelated Code/Cowork answers

Windows field test:
- Real Bash pwd succeeded, and returned /d/Work/Software/Claude-proxy.
- Model ignored requested cat README.md and searched unrelated Chinese
  "New Project" text instead.
- For FA-527 and ZH-884 simple instructions it returned unrelated
  GitHub/project-search prompts. These are real functional failures.
- It is not proven whether an upstream server mixes concurrent sessions,
  client chat history was attached, or the upstream model ignored the
  most recent instruction.
- Existing PR #18 reduced unwanted web tool injection and preserved
  client-owned Read/Bash tools; it cannot force third-party models to
  interpret instructions correctly.

New, EXPLICIT "Test upstream model instructions (2 requests)" button
sends two FIXED, synthetic Persian and Chinese prompts to the configured
default upstream model directly via HTTP, with one user turn each and
NO system prompt, chat history, tools, browser, shell, file access,
web proxy or client session. The button reports the model ID, marker
pass/fail, tool-call count, and first 240 returned characters. Each
click invokes TWO real model completions, potentially incurring fees.

Interpretation:
- If this isolated direct probe fails, investigate the provider's
  model routing, response quality, concurrency/session reuse and
  Chat Completions implementation first.
- If both isolated probes pass but Claude Code/Cowork fails, compare
  gateway request metadata (preflight context/message/tool counts),
  actual client conversation and tool results. The proxy/client
  adapter or tool semantics may be the cause.
- If an isolated probe passes, it proves only that tiny test succeeds;
  it DOES NOT guarantee long-context Code/Cowork behavior.
- Never treat model text alone as proof of executing a tool. Confirm
  exact tool_call/tool_result observations.
- The probe result separately shows the requested model, the model ID
  *reported by the upstream response* (or unreported), and response ID (or
  unreported). Do not treat the requested model as proof of actual routing.
- PASS is a conservative smoke check: the marker must be at the end,
  at least two characters of the expected Persian/Chinese writing script
  must be present, and no tool calls may be returned. This does not prove
  complete language comprehension or tool fidelity.
- When an Anthropic user content array mixes tool_result and fresh text,
  Chat Completions must receive the tool message immediately after the
  corresponding assistant tool_call, then a separate user message containing
  the additional instruction. Otherwise the upstream may reject the tool
  transcript or lose grounding. A dedicated regression covers this ordering.

## Windows acceptance

1. Back up the saved app settings, Quit the old app and extract the
   new Portable artifact on disk. Run the new EXE by double-clicking.
2. Do NOT clear HTTPS_PROXY in PowerShell. Leave the old dead proxy
   defined. Ping and model discovery must use direct provider access.
3. Confirm localhost gateway still uses 18183 and the API answers a
   plain new Claude Desktop conversation.
4. Check the separate TCP and API response times in Provider connection.
5. Open Provider connection and click the optional isolated model probe.
   Check both marker replies and the exact upstream model shown.
6. In fresh Claude Code/Cowork chats, repeat the README.md Read test
   and the FA-527/ZH-884 language-only instructions.
7. Set Web Search to Manual proxy ONLY if v2rayN has an active HTTP
   or SOCKS listener and testing requires web search. This does NOT
   modify provider API connectivity. Do not forward provider traffic
   over that manual search proxy.
8. Record differences between isolated direct model output and
   Claude Code/Cowork output before judging provider vs adapter.

Do not merge to main until real Windows acceptance and security review
are finished. This version remains a Draft stacked on PR #19.
