# راه‌اندازی امن Runner شخصی برای Claude Proxy

## چرا قبلاً از سرور شخصی استفاده نشد؟

در workflowهای قبل `windows-latest` و `ubuntu-latest` مشخص شده بود. اینها GitHub-hosted هستند؛ GitHub به‌صورت خودکار از runner شخصی یک مخزن دیگر استفاده نمی‌کند.

پس از عمومی‌شدن مخزن، اجرای دوباره GitHub-hosted شروع شد (شکست بدون حتی یک step دیگر اتفاق نیفتاد). با عمومی‌بودن مخزن، استفاده از GitHub-hosted استاندارد برای ریپازیتوری عمومی مشمول رایگان‌بودن زمان اجرای استاندارد است، مطابق سیاست جاری GitHub.

## سیاست امنیتی

**هرگز اجرای خودکار کد pull requestهای عمومی را روی سرور شخصی فعال نکنید.** Pull request ناشناس می‌تواند کد و اسکریپت نصب/تست دلخواه اجرا کند و به سرور شما آسیب بزند.

Workflow `verify-v2.yml` اکنون دو حالت دارد:

- **رویداد pull_request (به‌صورت خودکار):** Frontend روی `ubuntu-latest` و تست‌های Windows Rust روی `windows-latest`؛ امنیت Runner شخصی حفظ می‌شود.
- **رویداد workflow_dispatch (اجرای دستی):** ورودی `linux_runner` با گزینه‌های `github-hosted` و `self-hosted`. فقط مالک مخزن مجاز است برای اجرای دستی حالت `self-hosted` را انتخاب کند. در این حالت فقط `v2-frontend` روی `[self-hosted, linux, x64]` اجرا می‌شود و تست Rust/ساخت Windows Portable روی Windows GitHub-hosted باقی می‌ماند.

> GitHub در حالت معمول `workflow_dispatch` را فقط زمانی در دسترس قرار می‌دهد که workflow مربوطه روی شاخه پیش‌فرض وجود داشته باشد. این تغییر فعلاً در Draft PR است؛ تا زمان تأیید و ورود مجاز workflow به `main` ممکن است دکمه اجرای دستی جدید در Actions دیده نشود. **بدون تأیید مالک PR را Merge نکنید.**

## اتصال Runner موجود به این مخزن

1. به [تنظیمات Runner مخزن](https://github.com/soltan-developer/Claude-proxy/settings/actions/runners) بروید و بررسی کنید که یک Linux x64 Runner با برچسب `self-hosted` وضعیت `Idle` و `Online` دارد.
2. اگر Runner موجود شما روی `saadegi-site` به‌صورت *repository-scoped* نصب شده، به‌صورت پیش‌فرض در `Claude-proxy` قابل استفاده نیست. برای این مخزن یک Runner جدا در **پوشه و سرویس مستقل** روی سرور نصب کنید. Runnerهای همان پروژه را حذف یا جایگزین نکنید.
3. در صفحه بالا **New self-hosted runner → Linux → x64** را بزنید و دستورات تولیدشده GitHub را روی سرور اجرا کنید. توکن ثبت‌نام کوتاه‌عمر و محرمانه است؛ آن را در Issue، لاگ، چت یا فایل مخزن قرار ندهید.
4. برچسب‌های `self-hosted`, `linux`, `x64` باید در بخش Runner وجود داشته باشند. از روی آن‌ها فقط Linux jobs اجرا می‌شوند. اگر نیاز دارید چند Runner روی یک ماشین باشند، برای هرکدام مسیر نصب و سرویس جدا داشته باشید.
5. پس از قرار گرفتن workflow روی شاخه پیش‌فرض با تأیید شما، از **Actions → Verify v2 contracts → Run workflow** حالت `self-hosted` را انتخاب کنید و اجرا را روی یک شاخه مورداعتماد انجام دهید.
6. در جزئیات Job `v2-frontend`، قسمت Runner name باید نام Runner شخصی را نشان دهد؛ فقط وجود `self-hosted` در YAML به معنی اجراشدن روی سرور شما نیست.

## چرا Windows Portable روی Runner لینوکسی اجرا نمی‌شود؟

`build-portable.yml` از PowerShell و ابزارهای Tauri/Rust ویندوز برای EXE استفاده می‌کند. یک Runner لینوکسی به‌تنهایی آن محیط را فراهم نمی‌کند؛ بنابراین برای جلوگیری از ساخت خراب، Job ویندوز فعلاً `windows-latest` می‌ماند. برای انتقال این قسمت، لازم است یک Runner ویندوزی سازگار جداگانه معرفی و روی ویندوز آزمایش شود.

## معیار پذیرش

- تمام تست‌ها و نسخه هماهنگ روی Commit ثابت PASS باشند.
- اگر Runner شخصی انتخاب شد، `runner_name` دقیقاً به آن اشاره کند.
- هیچ PR ناشناس به‌صورت خودکار روی Runner شخصی اجرا نشود.
- هیچ کلید مخفی، توکن یا تنظیمات کاربران تغییر نکند.
- بدون تأیید مالک، PR ادغام و Release عمومی ساخته نشود.
